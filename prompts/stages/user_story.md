# 用户故事生成阶段模板

## 阶段概述
作为资深产品经理，请基于输入生成高质量的用户故事与 Gherkin 验收标准，为后续的产品需求文档和开发工作奠定基础。

## 输入参数
- **项目名**: {PROJECT_NAME}
- **目标用户**: {AUDIENCES}
- **业务目标**: {GOAL}
- **约束条件**: {CONSTRAINTS}
- **截止时间**: {DEADLINE}

## 输出要求

### 1. 用户故事 (至少 3 条)
每条用户故事必须包含：
- **作为** [用户角色]
- **我想** [功能描述]
- **以便** [业务价值]

#### 主要用户故事 (Must Have)
- 核心功能，用户必须能够完成的主要任务
- 直接影响业务目标的关键功能

#### 次要用户故事 (Should Have)
- 重要但不是核心的功能
- 提升用户体验的辅助功能

#### 极端情况用户故事 (Could Have)
- 边界条件和异常情况
- 特殊场景和高级功能

### 2. Gherkin 验收标准
每条用户故事必须包含完整的 Gherkin 格式验收标准：

```gherkin
Given [前置条件]
When [用户操作]
Then [预期结果]
And [附加验证]
```

### 3. 非功能需求草单
基于 {NON_FUNC_TARGETS} 要求，列出：
- **性能要求**: 响应时间、并发用户数、吞吐量
- **可用性要求**: 系统可用性、故障恢复时间
- **安全要求**: 数据加密、访问控制、审计日志
- **可观测性要求**: 监控指标、日志级别、告警策略
- **可访问性要求**: 键盘导航、屏幕阅读器、色彩对比度

### 4. 风险与假设清单
- **技术风险**: 技术实现的复杂度和不确定性
- **业务风险**: 市场接受度和竞争压力
- **时间风险**: 交付时间的不确定性
- **资源风险**: 人力、资金、时间资源
- **假设条件**: 技术假设、业务假设、用户假设

## 注意事项

### 用户故事编写原则
- **用户导向**: 从用户角度思考问题
- **价值驱动**: 每个故事都要有明确的业务价值
- **可测试性**: 验收标准必须可验证
- **独立性**: 故事之间相互独立
- **可协商性**: 故事可以进一步讨论和细化

### 验收标准编写原则
- **具体性**: 描述具体明确
- **可测量**: 结果可以客观测量
- **可达成**: 在合理时间内可以达成
- **相关性**: 与业务目标相关
- **时限性**: 有明确的时间要求

### 非功能需求编写原则
- **可测量**: 指标具体可测量
- **可验证**: 要求可以验证
- **可达成**: 在技术约束下可实现
- **可维护**: 要求易于维护和更新

### 风险识别原则
- **全面性**: 覆盖技术、业务、时间、资源等各方面
- **具体性**: 风险描述具体明确
- **可评估**: 风险影响可以评估
- **可应对**: 风险有应对策略

## 示例参考

### 用户故事示例
```
### US-001: 用户注册
**作为** 新用户  
**我想** 使用邮箱和密码注册账户  
**以便** 能够使用系统的核心功能

**验收标准 (Gherkin):**
```gherkin
Given 用户访问注册页面
When 用户输入有效的邮箱和密码
And 点击注册按钮
Then 系统创建新用户账户
And 显示注册成功消息
And 跳转到登录页面
```

**优先级:** Must Have  
**估算:** 5 故事点
```

### 非功能需求示例
```
### NFR-001: 性能
- 响应时间 < 2 秒 (P95)
- 并发用户数 > 1000
- 吞吐量 > 500 TPS
- 数据库查询时间 < 100ms
```

### 风险示例
```
### 技术风险
- **风险:** 第三方服务依赖可能导致系统不稳定
- **影响:** 系统可用性下降
- **缓解:** 实现服务降级和重试机制
```
